# Контракт: OpenAPI и типы во фронте

Status: ready-for-agent
PRD: .scratch/backend/PRD.md

Вход каждого эндпоинта проверяется zod-схемой, из тех же схем собирается
OpenAPI и раздаётся по `/api/openapi.json`. Списки разделов и цветов живут в
схеме перечислениями — сервер сверяет по ним, фронт получает их типами.

Во фронте появляется команда, которая тянет схему и генерирует `.d.ts`.
Сгенерированный файл коммитится: иначе сборка фронта начинает требовать живой
API.

## Приёмка

- `yarn api:types` во фронте обновляет типы, `astro check` проходит.
- Переименование поля в API ломает типизацию фронта на следующей генерации, а не
  в рантайме на живой странице.

## Comments

**Сделано.** Схема живёт по `GET /api/openapi.json`, фронт тянет её командой.

В API появились zod-схемы **ответов** (`src/catalog/schemas.ts`) — раньше это
были просто интерфейсы TypeScript, и OpenAPI из них не собрать. Теперь и типы, и
документ, и проверка ответа растут из одного места: `z.toJSONSchema` даёт JSON
Schema, `src/openapi/document.ts` собирает из неё документ OpenAPI 3.1. Списки
разделов, цветов, сортировок и значений Bluetooth попали в схему перечислениями —
фронт получает их типами, а не строками.

Во фронте:

- `yarn api:types` — `scripts/api-types.mjs`: тянет схему, генерирует
  `src/types/api.d.ts` и сразу прогоняет его через Prettier, чтобы файл не
  разъезжался с форматированием проекта. Адрес схемы — `API_SCHEMA_URL`,
  умолчание `http://localhost:3000/api/openapi.json`.
- `src/scripts/api.ts` — тонкий клиент: типы запросов и ответов выведены из
  сгенерированных, ошибки API превращаются в `ApiError` с кодом и сообщением.
  Его и будет звать SSR в задаче 07.

**Проверено, что контракт правда держит.** Схема с переименованным `imagePath`
→ `imageSrc` скормлена генератору, после чего `astro check` упал ровно на
`first.imagePath` — то есть расхождение ловится сборкой, а не пустой страницей в
браузере. Схема и типы возвращены на место, временный потребитель удалён.

`astro check`, `eslint`, `prettier --check` на фронте — чисто.
