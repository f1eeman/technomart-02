# GET /api/products

Status: ready-for-agent
PRD: .scratch/backend/PRD.md

Выдача считается в SQL: раздел, диапазон цены, набор цветов (внутри — «или»),
признак Bluetooth с третьим значением «не важно», сортировка по цене,
популярности и типу в обе стороны, страницы по четыре.

Ответ несёт товары, общее число и признак последней страницы.

**Границы слайдера цены отдаются отдельно от выдачи** и считаются по всему
разделу без учёта фильтра цены. Иначе после первой же фильтрации слайдер
схлопнется в текущий диапазон — сейчас фронт берёт их через `Math.min`/`Math.max`
по всем товарам раздела.

Умолчания в адрес не попадают, как и раньше: пустой запрос означает «цена во весь
диапазон, цвета все, Bluetooth не важен, по цене, по возрастанию, страница
первая».

## Приёмка

- Ответы совпадают с нынешним поведением `src/scripts/catalog.ts` на десятке
  сравнительных случаев, включая пустую выдачу.
- Неизвестный раздел даёт 404, битый параметр — 400 в общем формате ошибки.
- Номер страницы за пределами выдачи отдаёт пустой список, а не ошибку.

## Comments

**Сделано.** Два адреса: `GET /api/products` и
`GET /api/categories/:slug/price-range`.

Параметры повторяют адресную строку каталога один в один — `category`, `min`,
`max`, `colors`, `bt`, `sort`, `dir`, `page`, — и умолчания те же. Проверяет их
zod, раздел сверяется со списком из шести (в базу разделы не едут).

Две тонкости, которые пришлось решить отдельно:

- **Порядок при равных значениях.** Во фронте сортировка стабильная, то есть при
  равной цене товары остаются в порядке каталога. В SQL такого обещания нет,
  поэтому вторым ключом всегда идёт `id`, а он совпадает с порядком сида.
- **Сортировка по типу.** `localeCompare(…, 'ru')` и порядок Postgres по
  умолчанию — разные вещи. Русская коллация `ru-RU-x-icu` повешена на колонку
  `kind` отдельной миграцией, так что обычный `ORDER BY` даёт нужный порядок.
  Проверено, что Prisma на это не ругается: следующая `migrate dev --create-only`
  выдаёт пустую миграцию, расхождения схемы нет.

Границы цены считаются по всему разделу и отдаются отдельным адресом: если
считать их по отфильтрованной выдаче, ползунок схлопнется после первой же
фильтрации. Для моноподов — 500 и 24900, для квадрокоптеров — 5900 и 149000,
ровно как во фронте.

**Сверка с нынешним поведением.** Написан разовый скрипт, повторяющий
`matches`/`compare`/разбивку из `src/scripts/catalog.ts`, и прогнан на двенадцати
наборах параметров: страницы 1–3, сортировки по цене, популярности и типу в обе
стороны, фильтр по двум цветам, по Bluetooth, по диапазону цены, другой раздел и
две пустые выдачи. Совпали все двенадцать — и состав страницы, и `total`, и число
страниц. Скрипт удалён: он был нужен на время переноса.

Краевые случаи:

- неизвестный раздел — 404 `not_found`
- битая сортировка, нечисловая цена, нулевая страница — 400 с перечнем полей в
  `details`
- `min` больше `max` — 400 с внятной фразой
- страница за пределами — 200 и пустой список

**Расхождение с фронтом, сделанное намеренно.** Клиент при `page` больше
последней зажимает номер к последней странице. API так не делает: отдаёт пустой
список и кладёт в ответ `page`, `totalPages` и `isLast`, чтобы клиент поправился
сам. Прятать это внутри API значило бы врать про то, что было запрошено.
