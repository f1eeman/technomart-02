# Astro переходит на SSR

Status: ready-for-agent
PRD: .scratch/backend/PRD.md

Адаптер `node`, весь сайт строится на запрос. Страницы каталога, поиска, карточки
товара, корзины и сравнения берут товары из API вместо `src/data/catalog.ts`.
Разделы, цвета и слайды остаются в коде фронта.

`getStaticPaths` уходит оттуда, где страниц больше нет на диске; правило про
обязательный `interface Props` при этом остаётся в силе для всего, что принимает
`Astro.props`.

nginx раскладывает `/` на Astro, `/api` — на Express, `/uploads` — на файлы.

## Приёмка

- Полная высота главной и каталога совпадает с оригиналом: 2830px и 2035px.
- `docs/deploy.md` переписан: порядок запуска, миграции, переменные окружения,
  что делать при откате.
- SPA-фолбэк по-прежнему не включён, несуществующий путь отвечает 404.

## Comments

**Сделано.** Сайт — Node-приложение: `output: 'server'`, адаптер
`@astrojs/node` в режиме standalone. `getStaticPaths` больше нет ни в одной
странице.

Что откуда берётся теперь:

- раздел каталога — `GET /api/products` плюс `GET /api/categories/:slug/price-range`
- каталог целиком — `GET /api/categories` (счётчики в плитках)
- карточка товара — `GET /api/products/:slug`
- корзина и сравнение — `GET /api/products/all`
- поиск — `GET /api/search`, клиентский `search.ts` удалён

Разделы, цвета, производители и слайды остались кодом фронта: `catalog.ts`
похудел с 800 строк до 94 и стал справочником. Тип раздела теперь выводится из
контракта API (`CategorySlug`), так что выкинутый на сервере раздел уронит
`astro check`.

Попутно пришлось поправить то, что раньше держалось на клиентском JS:

- ссылки сортировки и страниц строились как `?sort=…` и затирали остальные
  параметры. Теперь их собирает `src/scripts/catalog-url.ts` из полного
  состояния, и умолчания в адрес по-прежнему не попадают.
- поле поиска в шапке заполняет сервер, а не скрипт.
- страница поиска рендерит найденное сразу: «Нашлось N», пустой ответ и
  подсказки — три разных состояния, посчитанные на сервере.

Неизвестный раздел, несуществующий товар и мусорный адрес отвечают 404 через
`Astro.rewrite('/404')`.

**Приёмка по высоте пройдена:** главная 2830px, каталог 2035px — ровно как у
оригинала.

Проверено обходом живой связки в контейнерах (`db → migrate → api → web`):

```
200  /            200  /catalog          200  /catalog/monopods
200  /product/…   200  /cart             200  /compare
200  /search?q=…  404  /catalog/spaceships  404  /product/nope  404  /nope
```

`docs/deploy.md` переписан целиком: состав служб, порядок выкладки (миграции →
api → web), переменные, nginx с проксированием `/api` и `/uploads`, заголовки
кэша. SPA-фолбэк по-прежнему не включается.

**Три вещи, на которых спотыкались.**

1. `@astrojs/node@11` требует `astro ^7.2.1`, а было закреплено `~7.1.6` —
   поднял до `~7.2.1` (в lock-файле 7.2.10). Иначе сервер падает с `app.getLogger is not a function`.
2. `API_BASE` сначала был объявлен `access: 'public'` — Astro подставил значение
   на этапе сборки, и образ ходил на `localhost` разработчика. Нужен
   `access: 'secret'`, он читается в рантайме.
3. `@typescript-eslint/no-misused-promises` падает (не ругается, а именно падает)
   на `return Astro.rewrite(…)` во фронтматтере — это `return` на верхнем уровне
   модуля. Правило выключено для `.astro`, причина записана в `CLAUDE.md`.

**Что осталось выключенным до задачи 08.** Старый `initCatalog` со страницы
раздела снят: он рассчитан на все 38 карточек в разметке, а сервер теперь отдаёт
четыре. Фильтр пока неинтерактивен — сортировка и страницы работают ссылками.
